### Shipping

**You own what lands. Verify each PR against the real surface, land only the contiguous verified run from the bottom, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Check the branch out at its head, not your working copy. Run the change end to end, or drive the UI, on the surface a user would touch. Post `PASS`, `PASS+NOTES`, or `FAIL` as a review comment on the PR you checked. One thread wrote the code and verifies it, so the check has to be evidence a wrong implementation could not produce: pasted run output, a screenshot of the flow, a query result, the failing repro now passing. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own, behind a fresh verdict, since its old one ran with that code beneath it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, the earlier result stands if what it ran builds the same at both SHAs apart from noise, where noise is a difference that also shows up between two builds of the same SHA, or an embedded commit SHA. Report each kind of noise with its files so a reader can check the call. The change itself still gets fresh checks, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `gh pr merge <pr> --squash`. A PR whose base is still its parent's branch merges into that branch, not trunk, so read the PR back with `gh pr view <pr> --json state,mergedAt,baseRefName`: a merge command can report success when a merge queue only queued it, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base. Arm `--auto` only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk with `gh pr edit <pr> --base trunk`, move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Poll `gh pr view <pr> --json state,mergeCommit` until every PR in the run reads `MERGED`. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and the evidence behind it, what landed and how you confirmed it, and what the next gap needs.
