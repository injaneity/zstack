### Hourly

**The chat's whole routine is "run zstack hourly at main; relay what it returns".** This is that pass. It runs on the relay host (the mini), which reaches the VM through `bin/hourly on vm …`; the VM cannot reach the mini. Linear is the chat's own tool, so the chat runs the Linear steps and passes the Todo ids in. The pass orchestrates only: it never edits, builds or pushes, as onigiri-mode's Chat orchestrator section says. Each host names its own host file in `~/.config/onigiri/host` (`mini`, `vm`), so no command needs `ONIGIRI_HOST`. Each one prints `zstack <sha>` first. Relay that sha with the outputs, so a pass on an old tree shows.

**Decide or ask (Zane, 11 Nov 16:58 SGT).** Decide these without asking, and log each: reruns of cancelled or stuck jobs; approving fork workflow runs on trycua/cua that await approval (Zane, 12 Nov 11:45 SGT); killing hung runs; pruning on the VM and the mini; PR titles (`fix(...)`/`feat(...)`, no `Co-authored-by`); filing real issues and opening verified fixes; whether verification is enough (the verifier owns it); best-practice design picks (pi researches and picks, and keeps current behaviour unless a change is needed). Bring only these to Zane: a deep or human preapproval, only once its PR is green at a stable head (the sha, one row each); patent or cua-staging; licensing; any message to teammates or outside people; money and credentials; a change to the hold, patent, merge or mac sign-off rules; an action on a review-only teammate's PR; widening a permission. A needs-Zane item that fits neither list goes to Zane.

Every decision gets one `bin/hourly log <host> <action> <item> <reason>` row in the hourly host's `pickup.log` (`ts_sgt host action item reason free_gb`, append-only). `bin/hourly launch` writes its own row.

0. **Cheap fingerprint.** `bin/hourly --linear <Todo ids, comma-separated>`. It moves the package to origin/main first, then reads both hosts' runs, parity and disk, our open trycua/cua PR heads, the other open PRs, the Linear ids and whether the batch is due. When nothing changed since the last `bin/hourly done` and nothing is actionable, it prints one `skip:` line. Then stop silently: no outputs and no row of your own. Every pass, skipped or not, writes one `pass` row with its Todo candidate count and free auto slots. Anything actionable never skips: an exited or lost run, a queued run (one back from a 429 only once its `resume_at` has passed), a hung run, a due batch, a `merge job:` line other than `ok`, or a free auto slot while the Todo list is not empty. That line is the merge job's last finished run from `tick/last-run` on its host: `stale` (none in the last 55 minutes, its 15-minute interval plus its 40-minute kill), `not ok` (that run logged errors), `paused` (`tick/PAUSED` is set) or `no last-run`. Anything but `ok` is a needs-Zane item, with the line.
1. **Completion queue.** On each host, `bin/hourly on <host> bin/pi-run list exited lost`. For each run, read `bin/hourly report <id>` (on the VM: `bin/hourly on vm bin/hourly report <id>`). Take its PR links, `follow-ups:` and `questions:` into the outputs and filing. Move its Linear issue (team Cua, named in the brief) to In Review when the run opened a PR, and to Done when it finished with nothing to merge. Then `bin/hourly on <host> bin/pi-run collect <id>`, and log a `collect` row with the rc and what it did. A lost run (KILL or OOM, no rc) sends its failed wake at this collect, since its supervisor died with pi. A collected id is final: a retry is filed again under a fresh id (`<id>-r`). A run its brief marks chat-started (`source: chat`) is collected the same way, and its result goes to the chat.
2. **Slots.** `config/slots.json` sets both caps, and `bin/hourly` prints them on its `slots:` line: `total` runs at once across both hosts, and `auto` of them may be hourly auto-launches (`source: auto`). The auto cap counts only auto-launches; chat-queued runs count only toward the total. Only a running run holds a slot. Never preempt: a running session is never stopped to free a slot. **Hung**: a running run with no log or session write for 3h (`HUNG?`). Look at its process tree. Kill a stuck child first (a finished bench's relay, a hung `sfltool`), and log `unstick` with the pid and why. A pi that is itself stuck is killed too (Decide or ask), with an `unstick` row; its run is then lost and collected in step 1. Never kill onigiri-linux or a VM a live session uses.
3. **Launch host.** The VM only when its `bin/hourly` line says at main and it has at least 20G free; otherwise the mini. A Linux-only task with no VM is skipped with a `skip` row naming the reason. On the mini, low disk is fixed by pruning what host-mini.md allows, never a live session's files. On the VM, prune finished sessions' build output and caches without asking (Decide or ask), never a live session's files. A task dir that may hold unpushed work is data, not cache (docs/HOST.md, Disk).
4. **Chat queue, first.** `bin/hourly queue`. It first gives each of our PRs that is red after the merge job's rerun back to the thread that pushed its head (`review/<id>/pushed`, written by cua's pre-push hook): `bin/pi-run ci` queues that collected run again with the failure, once per PR and head and at most `fix_attempts` heads per PR (`config/ci.json`), and logs a `ci-reopen` row. The drain below then resumes it in its own session, like a 429's continuation. A red head no run pushed prints `file an unstick` (step 6), and a thread whose fix attempts are spent prints `needs Zane`. Every host has its own queue (`bin/queue <id>` on that host, a `queued` `run.json` in its root), and this one command drains them all the same way: oldest `since=` first across the hosts, each run started on the host that queued it, while the shared slots allow (step 2), and on a peer only while step 3 says it can launch. A run that hit an upstream 429 is back in the queue with its first `since=`, and the drain resumes it in its own pi session once its `resume_at` has passed. That is never a failure and needs no message. It logs a `launch` or `resume` row per start and a `wait` row with the reason for each run that waits. Queued runs go before any Linear pick.
5. **Linear Todo, after the queue.** Team Cua only, and only for trycua/cua work: never file or pick a zstack, onigiri or tooling item. Pick the oldest highest-priority Todo the launch host can do. Exactly five rules skip a Todo, and no other reason does: it is held, it is owned by an open PR, it overlaps another live run, it waits on Zane, or the launch host can't do it. Unstick and review Todos, and ones that were filed in an earlier pass, are pickable like any other. Every skip writes one `skip` row per issue naming its rule, never one row for a group. Write the brief with `bin/new-brief <cua-id> <role> auto` (the issue title and link on stdin, plus "Kind:" and the PR to touch), launch it with `bin/hourly launch <cua-id> <host> auto, <why this one>`, and move the issue to In Progress. Only while auto slots are free.
6. **File.** Into Linear Cua, at most 10 new issues a pass, oldest first. The rest wait for the next pass, with a `file` row noting the cap. File these: a run's `follow-ups:`; an unstick for our PR with ci-gate red after its one rerun that `bin/hourly queue` could not give back to its thread (no run pushed that head), or a conflict; red main; a first review of a new PR or a new head from a teammate (f-trycua, ddupont808, 0xjohnnydev) or an outside contributor (ruicongg, astrovm, CMGS, anyone not on the team), CLA checked first; a salvage of a fixable outside PR. Never file for a bot (a `skip-author` row, any `[bot]` or `app/` login), or for a held PR or item (CUA-3499 and CUA-3673 stay local). Secrets and patent items stay out of Linear. Move an issue to Done once its PR merged, and cancel a review issue whose PR merged first.
7. **Stale PRs.** Close only our own (injaneity) PR, and only when main or another PR already has its change, and log `close` with what replaced it. A salvaged outside PR closes once the salvage merges, with a thank-you drafted through dumpling. Never close a teammate's PR or a held one (a `hold` row).
8. **Salvage or review.** Outside contributors (ruicongg, astrovm, CMGS and anyone not on the team): salvage a fixable PR instead of requesting changes, as a new PR of ours that credits them. A thank-you never says "landed" until the salvage merges. Teammates (f-trycua, ddupont808, 0xjohnnydev) are review-only, as Hard rules' Scope says: a first review and nothing else. A review task for one is filed, never cancelled.
9. **Daily preapprove batch.** The first pass after 08:00 SGT, while the snapshot says `due`. List our open PRs whose only merge blocker is a deep or human tier with no `preapprove` row at the head: green ci-gate at a stable head, no hold, no conflict, not a draft. Give each its full head sha, so his answer is one row each. That list is one needs-Zane item. Log `preapprove-batch` with the numbers, or `none`. When Zane answers with an explicit call, relay it as one row each with `bin/hold-row add` on the VM (docs/HOST.md, Holds file), then run `hosts/mini/sync-from-vm.sh`.
10. **Store.** `bin/hourly done --linear <the same ids>`. It runs after the pass, so a pass that dies halfway is redone next hour.

**Drafts go through dumpling.** Anything posted under Zane's name to someone else is a draft for dumpling: outside-contributor comments, thank-yous and teammate review comments. Send it as a dumpling ask with priority true; FYIs go with priority false. dumpling shows drafts only in Zane's chat with it, and the chat never relays them. Upstream or public posts go only through dumpling.

**Outputs.** Return exactly these four lists, each "none" when empty, after the `zstack <sha>` line and one line of slots and hosts. No status report: when all four are none, the pass sends nothing, as a skip does.
- **needs-Zane**: only what Decide or ask brings to him: merge-gate asks (deep or human with no preapproval, green at a stable head, the batch), holds to set or lift, a red PR whose thread spent its fix attempts, a host not at main, a merge job not `ok`, and disk the pass could not fix by pruning. Each run's `questions:` go here too, except one the decide list covers, which the pass decides and logs.
- **dumpling results**: what each collected run did, with PR URLs, for dumpling's FYI.
- **outside-contributor drafts**: comments and thank-yous for outside PRs, routed to dumpling.
- **teammate comment drafts**: first-review comments for teammate PRs, routed to dumpling.
