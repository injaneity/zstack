### Hourly

**The pickup runs on the mini, from a schedule, with no chat in the loop: `bin/pickup` (model/Pickup.tla).** `hosts/mini/install-pickup.sh on` loads a launchd StartInterval job (`[pickup]` `interval_s` in `config/policy.toml`, no KeepAlive) that runs one pass: collect (step 1), `bin/hourly queue` (step 4), then step 5 from GitHub instead of Linear. Its candidates are trycua/cua issues assigned to us (`[people]` `me` in `config/policy.toml`), open PRs requesting our review, directly or through one of its teams (one first review per head) and our PRs the merge job leaves to a session that no thread took back (one unstick per head), `urgent` first, then oldest, while the auto pool has room. Run state is the record that a candidate was taken: a review id (`cua-<n>`, `cua-<n>-review-<head7>`, `cua-<n>-unstick-<head7>`) on either host, or its `launch` row in `pickup.log`. It writes nothing to GitHub or Linear. The same five rules skip, one `skip` row each. It wakes the chat (`done`, or `failed` when the pass died or hit `deadline_s`) only with something new: a collected run's results, questions, follow-ups and drafts, or a needs-Zane item no delivered wake carried. The wake's `report=` file has the lists below, plus `chat:` for what the chat decides itself: follow-ups to file, hung runs and disk to prune. A pass with nothing new sends nothing. `bin/pickup --dry` prints a pass's plan and changes nothing. The steps below stay the chat's for what a script can't decide: steps 2 (hung runs), 6 to 9, and relaying the lists. A chat pass runs `bin/hourly queue` and launches like the timer, under the same caps.

**The chat's routine, while it still runs, is "run zstack hourly at main; relay what it returns".** This is that pass. It runs on the relay host (the mini), which reaches the VM through `bin/hourly on vm …`; the VM cannot reach the mini. Linear is the chat's own tool, so the chat runs the Linear steps and passes the Todo ids in. The pass orchestrates only: it never edits, builds or pushes, as onigiri-mode's Chat orchestrator section says. Each host names its own host file in `~/.config/onigiri/host` (`mini`, `vm`), so no command needs `ONIGIRI_HOST`. Each one prints `zstack <sha>` first. Relay that sha with the outputs, so a pass on an old tree shows.

**Decide or ask (Zane, 11 Nov 16:58 SGT).** Decide these without asking, and log each: reruns of cancelled or stuck jobs; approving outside-contributor (fork) workflow runs on trycua/cua that await approval (Zane, 12 Nov 11:45 SGT); killing hung runs; pruning on the VM and the mini; PR titles (`fix(...)`/`feat(...)`, no `Co-authored-by`); filing real issues and opening verified fixes; whether verification is enough (the verifier owns it); best-practice design picks (pi researches and picks, and keeps current behaviour unless a change is needed). Bring only these to Zane: a preapproval for a `[merge]` `preapprove_tiers` tier, only once its PR is green at a stable head (the sha, one row each); patent or cua-staging; licensing; any message to teammates or outside people; money and credentials; a change to the hold, patent, merge or mac sign-off rules; an action on a review-only teammate's PR; widening a permission. A needs-Zane item that fits neither list goes to Zane.

Every decision gets one `bin/hourly log <host> <action> <item> <reason>` row in the hourly host's `pickup.log` (`ts_sgt host action item reason free_gb`, append-only). `bin/hourly launch` writes its own row.

0. **Cheap fingerprint.** `bin/hourly --linear <Todo ids, comma-separated>`. It moves the package to origin/main first, then reads both hosts' runs, parity and disk, our open trycua/cua PR heads, the other open PRs, the Linear ids and whether the batch is due. When nothing changed since the last `bin/hourly done` and nothing is actionable, it prints one `skip:` line. Then stop silently: no outputs and no row of your own. Every pass, skipped or not, writes one `pass` row with its Todo candidate count and free auto slots. Anything actionable never skips: an exited or lost run, a queued run (one back from a 429 only once its `resume_at` has passed), a hung run, a due batch, a `merge job:` line other than `ok`, or a free auto slot while the Todo list is not empty. That line is the merge job's last finished run from `tick/last-run` on its host: `stale` (none within `[hourly]` `merge_stale_min` in `config/policy.toml`, its cron interval plus its kill), `not ok` (that run logged errors), `paused` (`tick/PAUSED` is set) or `no last-run`. Anything but `ok` is a needs-Zane item, with the line.
1. **Completion queue.** On each host, `bin/hourly on <host> bin/pi-run list exited lost`. For each run, read `bin/hourly report <id>` (on the VM: `bin/hourly on vm bin/hourly report <id>`). Take its PR links, `follow-ups:` and `questions:` into the outputs and filing. Move its Linear issue (team Cua, named in the brief) to In Review when the run opened a PR, and to Done when it finished with nothing to merge. Then `bin/hourly on <host> bin/pi-run collect <id>`, and log a `collect` row with the rc and what it did. A lost run (KILL or OOM, no rc) sends its failed wake at this collect, since its supervisor died with pi. A collected id is final: a retry is filed again under a fresh id (`<id>-r`). A run its brief marks chat-started (`source: chat`) is collected the same way, and its result goes to the chat.
2. **Slots.** Two pools, counted apart across both hosts (Zane, 12 Nov 12:47 SGT; his words are in `config/policy.toml`'s `[slots]` comment). `[slots]` sets `auto` (hourly picks, `source: auto`) and `hand` (everything the chat starts, through `bin/pi-run` or `bin/pi-run queue`), and `bin/hourly` prints both on its `slots:` line. Each run is tagged with its pool in `run.json` when it is queued or starts, from its brief; a running run with no tag counts as hand. The quick-check lane (`source: quick`, or role research) is in neither pool. A hand launch past its pool, or while a host's runs are unknown, is queued instead and `bin/pi-run` says so; the drain starts it once the pool has room, and `bin/hourly launch` logs a `wait` row for a pick the auto pool has no room for. Only a running run holds a slot. While a host is unreachable its runs are unknown, so the `slots:` line shows no auto slot free and step 5 picks nothing. Never preempt: a running session is never stopped to free a slot. **Hung**: a running run with no log or session write for `[hourly]` `hung_min` (`HUNG?`). Look at its process tree. Kill a stuck child first (a finished bench's relay, a hung `sfltool`), and log `unstick` with the pid and why. A pi that is itself stuck is killed too (Decide or ask), with an `unstick` row; its run is then lost and collected in step 1. Never kill onigiri-linux or a VM a live session uses.
3. **Launch host.** The VM only when its `bin/hourly` line says at main, it has at least `[hourly]` `floor_gb` free and no `pause:` line names it (an auto pause, docs/HOST.md); otherwise the mini. A Linux-only task with no VM is skipped with a `skip` row naming the reason. On the mini, low disk is fixed by pruning what host-mini.md allows, never a live session's files. From 13 Nov 2026 SGT (the 11 Nov retro; not before, while a bench uses a Lume guest): delete stopped `cua-e2e-*` lume VMs older than `[hourly]` `lume_prune_age_h` whose run is collected; never a running VM or a seed. `lume-e2e` names each worker `cua-e2e-<run id>` and prints `run=<run id>` in the session that started it, so its run is the review dir whose files name that id; a worker no collected run names is kept. The seed is `seed` in `~/.local/share/cua-lume-e2e/config.json`. Log one `prune` row per VM. On the VM, prune finished sessions' build output and caches without asking (Decide or ask), never a live session's files. A task dir that may hold unpushed work is data, not cache (docs/HOST.md, Disk).
4. **Chat queue, first.** `bin/hourly queue`. It first gives each of our PRs that is red after the merge job's rerun back to the thread that pushed its head (`review/<id>/pushed`, written by cua's pre-push hook): `bin/pi-run ci` queues that collected run again with the failure, once per PR and head and at most `fix_attempts` heads per PR (`config/policy.toml` `[ci]`), and logs a `ci-reopen` row. The drain below then resumes it in its own session, like a 429's continuation. A red head no run pushed prints `file an unstick` (step 6), and a thread whose fix attempts are spent prints `needs Zane`. Every host has its own queue (`bin/pi-run queue <id>` on that host, a `queued` `run.json` in its root), and this one command drains them all the same way: oldest `since=` first across the hosts, each run started on the host that queued it, while its pool has room (step 2), and on a peer only while step 3 says it can launch. A run that hit an upstream 429 is back in the queue with its first `since=`, and the drain resumes it in its own pi session once its `resume_at` has passed. That is never a failure and needs no message. It logs a `launch` or `resume` row per start and a `wait` row with the reason for each run that waits. Queued runs go before any Linear pick. Its last line, `queue: … auto free <n>`, is the auto slots step 5 may take.
5. **Linear Todo, after the queue.** Team Cua only, and only for trycua/cua work: never file or pick a zstack, onigiri or tooling item. Pick the oldest highest-priority Todo the launch host can do. Exactly five rules skip a Todo, and no other reason does: it is held, it is owned by an open PR, it overlaps another live run, it waits on Zane, or the launch host can't do it. Unstick and review Todos, and ones that were filed in an earlier pass, are pickable like any other. Every skip writes one `skip` row per issue naming its rule, never one row for a group. Write the brief with `bin/new-brief <cua-id> <role> auto` (the issue title and link on stdin, plus "Kind:" and the PR to touch), launch it with `bin/hourly launch <cua-id> <host> auto, <why this one>`, and move the issue to In Progress. Only while auto slots are free: the `auto free` count on step 4's `queue:` line, less this step's launches.
6. **File.** Follow-ups go to trycua/cua as GitHub issues, with the host's `gh` login, and never to Linear (Zane, 12 Nov: the pickup works from GitHub with no Linear key, and real, verified issues are filed). The pickup lists each run's `follow-ups:` under `chat:` as `follow-up to file`; the chat files the real ones, at most `[hourly]` `file_cap` a pass, oldest first, and the rest wait for the next pass with a `file` row noting the cap. Real means verified: the run saw it, not a guess. An open issue that already has it is not filed again; log a `file` row naming it. File with `gh issue create -R trycua/cua --assignee "$(bin/policy get people.me)"`, so the next pickup pass can take it like any assigned issue. Also file red main, and an unstick the pickup cannot take (a conflict). A first review or a salvage is not an issue: the pickup takes reviews from GitHub's review requests, and a review run's report says when a salvage is due. Never file for a bot (a `skip-author` row, any `[bot]` or `app/` login), or for a held PR or item. Secrets and patent items (`[patent]` `held_words` in `config/policy.toml`) never go into an issue.
7. **Stale PRs.** Close only our own (`people.me`) PR, and only when main or another PR already has its change, and log `close` with what replaced it. A salvaged outside PR closes once the salvage merges, with a thank-you drafted through dumpling. Never close a teammate's PR or a held one (a `hold` row). Issues close only as Hard rules' `issue-close` says, and a salvage's body follows `salvage-fixes` (`config/policy.toml` `[issues]`). The pickup's `chat:` list names what is left: an open salvage missing a `fixes` line (edit its body), an issue a merged salvage fixed but left open, and a source PR still open after its salvage merged. Close each with a comment naming the salvage, and log `close` with it.
8. **Salvage or review.** Outside contributors (ruicongg, astrovm, CMGS and anyone not on the team): salvage a fixable PR instead of requesting changes, as a new PR of ours that credits them. A thank-you never says "landed" until the salvage merges. Teammates (the holds file's `review-only` rows) are review-only, as Hard rules' Scope says: a first review and nothing else. A review run for one is never cancelled.
9. **Daily preapprove batch.** The first pass from `[hourly]` `batch_hour` SGT on, while the snapshot says `due`. List our open PRs whose only merge blocker is a tier in `[merge]` `preapprove_tiers` with no `preapprove` row at the head: a green `merge.gate_check` at a stable head, no hold, no conflict, not a draft. Give each its full head sha, so his answer is one row each. That list is one needs-Zane item. Log `preapprove-batch` with the numbers, or `none`. When Zane answers with an explicit call, relay it as one row each with `bin/hold-row add` on the VM (docs/HOST.md, Holds file), then run `hosts/mini/sync-from-vm.sh`.
10. **Store.** `bin/hourly done --linear <the same ids>`. It runs after the pass, so a pass that dies halfway is redone next hour.

**Drafts go through dumpling.** Anything posted under Zane's name to someone else is a draft for dumpling: outside-contributor comments, thank-yous and teammate review comments. Send it as a dumpling ask with priority true; FYIs go with priority false. dumpling shows drafts only in Zane's chat with it, and the chat never relays them. Upstream or public posts go only through dumpling.

**Outputs.** Return exactly these four lists, each "none" when empty, after the `zstack <sha>` line and one line of slots and hosts. No status report: when all four are none, the pass sends nothing, as a skip does.
- **needs-Zane**: only what Decide or ask brings to him: merge-gate asks (a `preapprove_tiers` tier with no preapproval, green at a stable head, the batch), holds to set or lift, a red PR whose thread spent its fix attempts, a host not at main, a merge job not `ok`, and disk the pass could not fix by pruning. Each run's `questions:` go here too, except one the decide list covers, which the pass decides and logs.
- **dumpling results**: what each collected run did, with PR URLs, for dumpling's FYI.
- **outside-contributor drafts**: comments and thank-yous for outside PRs, routed to dumpling.
- **teammate comment drafts**: first-review comments for teammate PRs, routed to dumpling.
