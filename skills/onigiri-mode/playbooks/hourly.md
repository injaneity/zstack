### Hourly

**The chat's whole routine is "run zstack hourly at main; relay what it returns".** This is that pass. It runs on the relay host (the mini), which reaches the VM through `bin/hourly on vm …`; the VM cannot reach the mini. Linear is the chat's own tool, so the chat runs the Linear steps and passes the Todo ids in. The pass orchestrates only: it never edits, builds or pushes, as onigiri-mode's Chat orchestrator section says. Run every command with `ONIGIRI_HOST=mini`. Each one prints `zstack <sha>` first. Relay that sha with the outputs, so a pass on an old tree shows.

Every decision gets one `bin/hourly log <host> <action> <item> <reason>` row in the hourly host's `pickup.log` (`ts_sgt host action item reason free_gb`, append-only). `bin/hourly launch` writes its own row.

0. **Cheap fingerprint.** `bin/hourly --linear <Todo ids, comma-separated>`. It moves the package to origin/main first, then reads both hosts' runs, parity and disk, our open trycua/cua PR heads, the other open PRs, the Linear ids and whether the batch is due. When nothing changed since the last `bin/hourly done` and nothing is actionable, it prints one `skip:` line. Then stop silently: no outputs and no log row. Anything actionable never skips: an exited, lost or queued run, a paused run whose `resume_at` has passed, a legacy dir, a hung run, or a due batch.
1. **Completion queue.** On each host, `bin/hourly on <host> bin/pi-run list exited lost`. For each run, read `bin/hourly report <id>` (on the VM: `bin/hourly on vm bin/hourly report <id>`). Take its PR links, `follow-ups:` and `questions:` into the outputs and filing. Then `bin/hourly on <host> bin/pi-run collect <id>`, and log a `collect` row with the rc and what it did. A run its brief marks chat-started (`source: chat`) is collected the same way, and its result goes to the chat. Legacy dirs (a `run.rc` and no `run.json`): read the report, then `bin/hourly processed <id>`.
2. **Paused runs.** A `paused` run hit an upstream 429. Once its `resume_at` has passed (the snapshot marks it `DUE`), `bin/hourly on <host> bin/pi-run resume <id>`, and log `resume`. It takes the run's own slot back, so a resume is not a new launch. It is never a failure and needs no message.
3. **Slots.** 5 run at once in total across both hosts, and 3 of them may be hourly auto-launches (`source: auto`). The auto cap counts only auto-launches; chat-queued runs count only toward the 5. Never preempt: a running session is never stopped to free a slot. **Hung**: a running run with no log or session write for 3h (`HUNG?`). Look at its process tree. Kill only a stuck child (a finished bench's relay, a hung `sfltool`), never pi itself, and log `unstick` with the pid and why. A pi that is itself stuck is a needs-Zane item. Never kill onigiri-linux or a VM a live session uses.
4. **Launch host.** The VM only when its `bin/hourly` line says at main and it has at least 20G free; otherwise the mini. A Linux-only task with no VM is skipped with a `skip` row naming the reason. On the mini, low disk is fixed by pruning what host-mini.md allows, never a live session's files. On the VM, list candidates and ask Zane (docs/HOST.md, Disk).
5. **QUEUED chat queue, first.** `pi-run list queued` on each host, oldest `since=` first. Launch each into a free slot with `bin/hourly launch <id> <host> chat queue`. Queued runs go before any Linear pick.
6. **Linear Todo, after the queue.** Team Cua only, and only for trycua/cua work: never file or pick a zstack, onigiri or tooling item. Pick the oldest highest-priority Todo the launch host can do, skipping one that is held, owned by an open PR, overlaps another live run or waits on Zane. Log every skip with its reason. Write the brief with `bin/new-brief <cua-id> <role> auto` (the issue title and link on stdin, plus "Kind:" and the PR to touch), launch it with `bin/hourly launch <cua-id> <host> auto, <why this one>`, and move the issue to In Progress. Only while auto slots are free.
7. **File.** Into Linear Cua, at most 10 new issues a pass, oldest first. The rest wait for the next pass, with a `file` row noting the cap. File these: a run's `follow-ups:`; an unstick for our PR with ci-gate red after its one rerun, or a conflict; red main; a first review of a new PR or a new head from a teammate (f-trycua, ddupont808, 0xjohnnydev) or an outside contributor (ruicongg, astrovm, CMGS, anyone not on the team), CLA checked first; a salvage of a fixable outside PR. Never file for a bot (a `skip-author` row, any `[bot]` or `app/` login), or for a held PR or item (CUA-3499 and CUA-3673 stay local). Secrets and patent items stay out of Linear. Cancel an issue whose PR already merged.
8. **Stale PRs.** Close only our own (injaneity) PR, and only when main or another PR already has its change, and log `close` with what replaced it. A salvaged outside PR closes once the salvage merges, with a thank-you drafted through dumpling. Never close a teammate's PR or a held one (a `hold` row).
9. **Salvage or review.** Outside contributors (ruicongg, astrovm, CMGS and anyone not on the team): salvage a fixable PR instead of requesting changes, as a new PR of ours that credits them. A thank-you never says "landed" until the salvage merges. Teammates (f-trycua, ddupont808, 0xjohnnydev) are review-only, as Hard rules' Scope says: a first review and nothing else. A review task for one is filed, never cancelled.
10. **Daily preapprove batch.** The first pass after 08:00 SGT, while the snapshot says `due`. List our open PRs whose only merge blocker is a deep or human tier with no `preapprove` row at the head: green ci-gate, no hold, no conflict, not a draft. That list is one needs-Zane item. Log `preapprove-batch` with the numbers, or `none`. Only Zane writes the holds file.
11. **Store.** `bin/hourly done --linear <the same ids>`. It runs after the pass, so a pass that dies halfway is redone next hour.

**Drafts go through dumpling.** Anything posted under Zane's name to someone else is a draft for dumpling: outside-contributor comments, thank-yous and teammate review comments. Send it as a dumpling ask with priority true; FYIs go with priority false. dumpling shows drafts only in Zane's chat with it, and the chat never relays them. Upstream or public posts go only through dumpling.

**Outputs.** Return exactly these four lists, each "none" when empty, after the `zstack <sha>` line and one line of slots and hosts:
- **needs-Zane**: merge-gate asks (deep or human with no preapproval, the batch), each run's `questions:`, holds to set or lift, a stuck pi, a host not at main, and disk the pass could not fix.
- **dumpling results**: what each collected run did, with PR URLs, for dumpling's FYI.
- **outside-contributor drafts**: comments and thank-yous for outside PRs, routed to dumpling.
- **teammate comment drafts**: first-review comments for teammate PRs, routed to dumpling.
