### Release bench

**You own one release's bench: NEW against OLD, both published cua-driver releases, and what happens on a regression.** Zane, 14 Nov 23:33 SGT: "lets bench releases instead of each individual pr, since it takes too long. we can just be aggressive with reverting our own prs". PRs no longer wait on a bench (Hard rules' `checks-bench`). This run is where a driver change meets the agent bench.

The pickup starts it (`bin/pickup`, `config/policy.toml` `[release_bench]`) when the release bot's "release cua-driver-rs X" merge has published release X: run id `release-bench-<NEW>`, OLD = the newest release benched before it. Releases that land while a bench runs are not benched on their own: the next pass benches the newest against the last one benched. Releases themselves stay with Francesco; this only benches published ones.

1. **Binaries.** Download NEW's and OLD's published assets with `gh release download` (the darwin-arm64 and linux-arm64-binary archives, the skills archive and `SHA256SUMS`), each into its own new directory, and check them against `SHA256SUMS`. Never build a release from source: the bench measures what users install.
2. **Harness.** The scripts are zstack's `hosts/mini/release-bench/` (its README has the layout). trycua/cua's Bench v2 runner (`libs/cua-driver-bench/automated-eval/macos_bench/run_bench.py --bench-v2`), arm `pi-cua-driver-main` only, model and harness as the last release bench used them (its report names them). Linux: the onigiri-linux VM's X11 lane through `launch/linux_session.sh`, harness at origin/main. macOS: a Lume bench guest cloned from the bench seed, the release installed into the bench's private app with `guest/install-driver.sh`. A lane exits non-zero when any of its runs is not DONE: rerun it to resume, and never call a bench done or a release benched until both lanes exit 0. Published binaries report an empty `git_sha`; pin that, and record the tag commit beside the rows.
3. **Serial, both platforms.** One trial at a time on the whole host: parallel benching is unverified (bench-parallel, 14 Nov), and the Linux VM is a guest on the mini, so the macOS lane runs first and the Linux lane after it ends. Every task of the v2 task set on each platform (foreground; macOS adds its background condition). Per task, both releases back to back with the same run indexes and seeds, the release that goes first alternating by task. Smoke one trial per lane first; it is not counted. A killed or paused run resumes with the same command.
4. **Decide.** Write the decision rule before reading a counted row. The standing one is `scripts/release-compare.py` (beside this playbook's skill): a regression is more paired pass losses than wins with a sign-test p under 0.05 on a platform-condition or overall, or a paired median ratio of tokens, turns or wall time whose bootstrap 95% interval lies wholly above 1.10 on a platform. Report pass rate, tokens, turns and wall time per platform and condition, with the paired wins and losses.
5. **On a regression, find the PR.** List the PRs merged between the two tags that touch `libs/cua-driver` (`git log OLD-tag..NEW-tag -- libs/cua-driver`). Narrow to the cause by bisect over those merges, or by a targeted rerun of the regressed task on builds with one suspect reverted, with the same seeds and the same serial rule. Name the PR only from that evidence.
6. **Revert our own, right away.** When the PR is ours (`people.me`), open a revert PR without asking (Hard rules' `merge-reverts`): `git revert -m 1 <merge sha>` on a branch off main, title `revert: <original title>`, the body says which task or behaviour regressed on which platform in plain words, with no numbers, and carries a `risk:` line. Run the verifier on it as for any PR. The tick merges it like any PR. When the PR is a teammate's or an outside contributor's, never revert it: list it under `questions:` for Zane with the evidence path.
7. **Record.** `report.md` in the run dir carries the verdict, the tables and the evidence paths. Only when both lanes exited 0 and the comparison's verdict is `regression` or `no regression` (not `inconclusive`), it ends with the line `benched: NEW against OLD`. The pickup counts NEW as benched, and so as the next baseline, only from that line in a run that exited 0. Bench numbers stay in report files: never in a PR, an issue, a commit or a public post. Stop any Lume guest you started; delete nothing.

**Reply:** the verdict (regression or not) for NEW against OLD, per platform, what regressed if anything, the revert PR URLs, and the report path.
