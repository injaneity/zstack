# subagent tool

`extensions/subagent/` gives pi a `subagent` tool. Each call starts a separate `pi` process with its own context window, runs one agent from `~/.pi/agent/agents/`, and returns the agent's final text. A call takes one `agent` and one `task`, plus `variant` for a role with several seats (the two designers).

It is pi 1.4.0's example extension, `examples/extensions/subagent/` in `@earendil-works/pi-coding-agent`, MIT, Copyright (c) 2025 Mario Zechner.

## What is removed

zstack only ever calls one agent with one task, so upstream's parallel (`tasks`) and chain (`chain`) modes are gone, with their concurrency limits and output truncation. So is its custom call and result rendering: pi's default renderer shows the call's arguments and the child's final text, collapsed to a few lines until expanded. The per-child token and cost tally went with it, since only that renderer showed it. `agents.ts` loads only `~/.pi/agent/agents/`: project-local agents, `agentScope`, `confirmProjectAgents` and their trust checks are gone (no session ever asked for them), with the `formatAgentList` export.

## The changes

All are in `index.ts`.

1. **Role prompts, not the session's rules.** `bin/pi-run` appends onigiri-mode's Hard rules to the parent only. The child's prompt temp file, passed as `--append-system-prompt`, holds its agent prompt, the no-polling line and one framing line, and nothing else (`buildChildPrompt` in `prompt.ts`). Each `agents/<name>.md` says where the child sits in the pipeline, which skill it loads, and quotes only the rules its role could break: `agents/verifier.md` is the one place that says what the verifier owns; the designer keeps the size and patent-hold rules in view; the read-only explorer needs none. The framing line tells the child its agent prompt is its whole role and that its tool limits win. The temp file is written for every child, even an agent with an empty body.
2. **Depth limit on the tool.** A child loads this same package, so it would get the tool again. The extension reads `PI_SUBAGENT_DEPTH` and registers nothing when it is 1 or more. Unset counts as 0. Any other value that is not a non-negative integer counts as 1, so garbage or `-1` keeps the tool off. Each child is spawned with the parent's value plus one. So a child cannot call the `subagent` tool. The bound is on the tool, not the process: a child's `bash` could still run `pi` (or `env -u PI_SUBAGENT_DEPTH pi`) and start another session.
3. **No sleep polling.** The child's prompt carries one line (`NO_POLLING_LINE` in `prompt.ts`) telling it not to use `sleep` or repeated polling to wait. Long waits are the tick's job.
4. **User agents only.** Only `~/.pi/agent/agents/` loads, so a repo cannot bring its own agents.
5. **Children get no forge or git credentials.** The child keeps the parent's environment except:
   - any variable whose name contains `TOKEN`, `SECRET`, `PASSW`, `CREDENTIAL`, `API_KEY`, `ACCESS_KEY`, `PRIVATE_KEY`, `AUTH` or `ASKPASS` is dropped, which covers `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GIT_ASKPASS` and `SSH_AUTH_SOCK`. Model-provider variables (`ANTHROPIC_*`, `CLAUDE_CODE_*`, `OPENAI_*`, `AWS_*`, `GOOGLE_*` and the other provider prefixes pi reads) are kept, because the child needs them to reach its model.
   - `GH_CONFIG_DIR` points at an empty per-child directory, so `gh` finds no stored login, and git's `gh auth git-credential` helper gets nothing either.
   - `GIT_TERMINAL_PROMPT=0`, so git fails instead of asking for a password.
6. **Dependency check at session start.** On `session_start` in a top-level session the extension checks three things: the agent files are in `<pi agent dir>/agents/`, they match the package's (a copy that differs is a warning naming `bin/install-agents.sh --force`, since `install-agents.sh` never overwrites and a role prompt can lag the package; the verifier is exempt because it always loads from the package), and `gh` is logged in when the working directory has a GitHub remote. With a UI, a missing agent file is one confirm that offers to run `bin/setup.sh`, and no is a valid answer. Without a UI (`pi -p`) it prints one stderr line per gap with the command that fixes it, and goes on. `gh` and a stale agent file are only ever warnings. Nothing is installed without a yes.
7. **Model by role.** The child's provider and model come from the package's `config/models.json`, keyed by agent name. A role whose value is a list has one seat per `variant`, 1-based, so `designer` variant 1 and variant 2 run on different providers. The child gets both `--provider` and `--model`, so a claude-code parent can start an openai-codex child. Before spawning, the tool resolves that seat's credentials in the parent's process, refreshing an expired OAuth token, through `ctx.modelRegistry.getApiKeyAndHeaders`. If that fails for the `verifier`, the tool returns an error and runs nothing: verification runs only on its own seat. For any other agent, the tool prints `subagent: WARNING <agent> cannot use <provider>/<model> (<reason>); falling back to the parent model <parent>` to stderr, puts the same line at the top of the tool result, and runs the child on the parent's provider, model and thinking level, even when the installed agent file names a `model:`. An agent with no config entry runs on the parent's model, or on its agent file's `model:` if it has one. No agent file in `agents/` names a model, and CI checks that.
8. **Child sessions are saved.** Upstream ran children with `--no-session`. Each child now gets `--session-id <parent id>-<agent>[-<variant>]-<stamp>` and `--name role:<agent>[:<variant>]` (with ` fallback` appended after a fallback), with `--session-dir ~/.pi/agent/sessions/subagents`, so its transcript and the provider and model of every reply are saved apart from top-level sessions (resume and `pi --continue` never pick one up), and `bin/check-models` reads them back against the config. The id ends with part of the tool call id, so two calls in one turn never share a file.

## What "read-only" means

pi enforces an agent's `tools:` list: `explorer`, `designer` and `verifier` get `read, grep, find, ls, bash` plus FFF's `fffind`, `ffgrep` and `fff-multi-grep` (where that package is installed; pi skips a listed tool that is not registered) and no `edit` or `write`. But `bash` is not sandboxed. A child can still write files through bash, run any local command, and reach the network. They keep `bash` because they need `git diff`, `git log`, `git show`, and for the verifier the repo's checks. So "read-only" is an instruction in each agent's prompt, not a boundary. The real bound is trust in that prompt plus the missing credentials: without a token, a child cannot push, merge, comment or close through `gh` or git over HTTPS. Credentials kept elsewhere on disk (an SSH key, a `.netrc`) are not hidden.

## Behaviour to know

- **Model.** Change 7. A seat that matches the parent's own provider and model skips the auth check and inherits the parent's thinking level. A seat on another provider runs at that provider's default thinking level.
- **Transcripts are saved.** Change 8. A child's session file is directly in `~/.pi/agent/sessions/subagents/` (no per-directory folder), and its header records the parent's working directory.
- **Agents are installed, not discovered.** The loader can't see a package's own `agents/`. Run `bin/install-agents.sh` to copy them into `~/.pi/agent/agents/`. The `verifier` is the exception: the tool always loads `agents/verifier.md` from the package, so an older installed copy is never used.
