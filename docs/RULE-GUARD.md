# rule-guard extension

`extensions/rule-guard/` turns the outright bans in onigiri-mode's Hard rules into code: a `tool_call` handler blocks the call and returns the reason, so the model sees a refusal it can act on. The matcher is `rules.ts`, a pure module, and `tests/rule-guard.test.ts` is the list of what is and is not blocked, case by case.

## What it blocks

1. **Force-push and skipping the pre-push hook.** `git push` with a force flag or a `+refspec`, `--no-verify`, and a `core.hooksPath` override on a push. The patent hold lives in the pre-push hook, so a hook skip is a patent-hold bypass.
2. **Merging or readying in a repo the queue owns.** One merge is let through: `gh pr merge <pr> --squash --match-head-commit <head>`, with the PR's number, each option once, and nothing else but `-R <repo>` and `--delete-branch`, when `bin/queue gate <pr> <head>` exits 0. That is the head the verifier passed as `auto` (or a preapproved item's), with `merge.gate_check` green, no check still running, no hold row and not a draft. A check still running would make `gh` arm auto-merge, which could then merge a later head. Every other form is refused as before: `gh pr merge`, `gh pr ready`, and the `gh api` and GraphQL calls that do the same, in every repo the config has (`repos` in `bin/policy dump`, which the extension reads once at load through `bin/policy dump`; if that fails, every merge and ready is refused in every repo, since the owned repo is then unknown). CI reruns (`gh run rerun`, with or without `--failed`, and the actions rerun API calls) are not blocked: the Hard rule `merge-reruns` has sessions decide reruns without asking, and only real failures go to the owner. The guard can't tell a runner network failure from a failure the diff caused, so the session makes that call. Approving a fork's workflow runs (`gh api -X POST repos/<merge.repo>/actions/runs/<id>/approve`) is not blocked either: the Hard rule `merge-fork-runs` lets sessions approve outside-contributor runs there so CI runs. Review still comes before any merge, and the merge job still merges. The repo comes from `-R`, a URL, the `gh api` path, `GH_REPO`, or the `origin` remote of every directory the command might run in. A repo that can't be told is blocked, so name it with `-R` to merge elsewhere from an owned checkout. When the launcher sets `ONIGIRI_READY_ALLOWED=1` for a thread whose brief says `merge: allowed`, `gh pr ready` runs; merges stay blocked. No launcher sets it for a T3 Code thread yet, so there `gh pr ready` is always refused. The guard reads the flag once at load and removes it from the environment, and refuses a bash command that names it other than as a bare `$ONIGIRI_READY_ALLOWED` read. Edit files that mention it with the `edit` tool.
3. **Closing an issue by hand without naming its PR.** In `merge.repo` (the config, read through the same `bin/policy dump`; if that fails, every hand close is refused), `gh issue close` runs only with a `--comment` that names a PR (`#123` or a pull URL) and no `not planned` or duplicate reason, as Hard rules' `issue-close` says. The REST (`state=closed`) and GraphQL (`closeIssue`) closes carry no comment, so they are refused there, as is a REST issue update whose body comes from `--input`, which the guard can't read. The guard can't tell that the PR is ours, merged, or fixed the issue; the session checks that. The repo is told the same way as for a merge, with issue URLs too. This rule leaves PR closes alone; 4 covers them.
4. **Closing a review-only teammate's PR or issue.** In `merge.repo`, `gh pr close`, `gh issue close`, and a `gh api` close of `issues/<n>` or `pulls/<n>` run only once the guard has asked GitHub who opened it (`gh api repos/<repo>/issues/<n>`, `.user.login`) and that login is not on a `review-only` row of a holds file it can read (`holds.ts`'s paths). Teammate PRs are review-only and never closed by us (Hard rules, Scope). A close it can't check is refused: no number or URL, a repo it can't tell, no holds file read, a failed author lookup, a GraphQL `closeIssue`/`closePullRequest`, or a `state` field or GraphQL query read from a file or stdin (`-F x=@file`, `--input`). The `review-only` rows are the owner's call.
5. **Writing the real holds file.** A `write` or `edit` of it, and bash that redirects into it, edits it in place, removes or moves it, or copies over it. Reads, diffs and copies out still run. The real holds files are `$ONIGIRI_ROOT/hold-prs.txt` (default `~/zstack`) and `host.holds` from the config (`holds.ts`), read once at load. A path is matched after resolving it against the command's directory and following symlinks, so a link to the file or to its directory counts, as does a hard link. A `hold-prs.txt` anywhere else, in a test root or a throwaway HOME, is an ordinary file. A path the guard can't resolve counts when its name is `hold-prs.txt`, in any case on macOS. That covers a variable, glob, brace or substitution, any path on a remote host, a path it can't walk (a symlink loop), and a relative path after a directory change it can't follow: a relative `cd` (which `$CDPATH` may redirect), `cd ~`, `cd -`, `pushd`/`popd`, a `cd` on a line with a substitution, and `env -C` or `sudo -D`. So a test root names its own `hold-prs.txt` by absolute path, or works from its own directory. The one sanctioned writer is `bin/hold-row`: `add '<row>'` appends a row relaying the owner's explicit call, and `retire` or `replace` comments out a stale row. The guard does not block it, since the command names no holds path, and the refusal message points to it.
6. **Moving the queue or marking a head verified from a coding thread.** In a session whose directory is a clone of a configured repo, `bin/queue` runs only as `release`, `gate`, `list`, `next` or `verified`, and a `gh api` write to a commit status or check run is refused. The dispatcher runs from the zstack package, so its calls pass. `queue verified` is the verifier's: `bin/queue` itself refuses it from the item's own thread, which it knows by the `T3CODE_THREAD_ID` the harness gives each session. So the guard refuses `queue verified` in a session that has no such variable, where the two can't be told apart, and refuses any command that sets or clears it.
7. **A PR title or body that breaks Commits and PR text.** In `merge.repo`, `gh pr create` and `gh pr edit` are refused when `--title` is not Conventional Commit syntax, or when the body (`--body`, or a `--body-file` the guard can read) has a `verify:` or `verify-ran:` line, a `Co-authored-by` trailer, or a path under `/home/<name>/` or `/Users/<name>/`. A title or body the guard cannot read (a shell variable, stdin, `--fill`) passes: this is a lint, and the model still has the rule. A title or body set through `gh api` is not checked.

The pre-push hook (`services/patent_push.py`) refuses a push whose commits add a `.onigiri.json`, a file under a `target/` directory, a new file without the SPDX header a same-type neighbour carries, or a `Co-authored-by` trailer on a commit made by the pushing identity. It reads the same range as the patent check. Model, agent and tool names in commit text are not checked, because a list of names would refuse honest commits about those tools.

Commands are split into simple commands and stripped of wrappers (`env`, `sudo`, `timeout`, `xargs`, ...) by `shell.ts`. The quoted command of `ssh`, `vm`, `bash -c`, `sh -c` and `eval` is checked too. A here-document body is data unless a shell reads it.

## Limits

It reads command text. A command built at run time (`eval "$cmd"`, a script file) is not seen, and neither is a write through Python or another interpreter. The pre-push hook and the repo's required checks stay the backstops. Children spawned by the `subagent` tool load the same package, so the guard binds them too.

The Claude Code hook also checks helpers. Claude's own Agent tool is refused for the explorer, designer and verifier, and a `delegate_task` call with the role `research`, `design` or `review` must name the model the machine file gives that role.
