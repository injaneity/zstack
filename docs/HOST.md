# One example host

This is how Zane's deployment runs zstack. It is one example, not a requirement: nothing outside `hosts/` reads these paths, and a fresh install needs none of them. This file and `hosts/` are the only places in the repo that name them.

## Machines

- **The box** runs the chat orchestrator. **The VM** (onigiri-linux) runs every pi session and the merge job. The relay Mac holds the VM's key. Its ssh wrapper is `hosts/mini/vm`, and `~/onigiri-vm/vm` is a symlink to it.
- Reach the VM from the box with `HOME=/home/box /srv/onigiri/tools/cua-main-88e6d9f do --no-record shell '~/onigiri-vm/vm "..."'`. For anything longer than a line, base64 a script over and run it as `bash /tmp/x.sh`. If the VM is unreachable, stop and ask Zane. Never do the work in the chat instead.
- `pi list` on the VM shows `git:github.com/injaneity/zstack`, checked out at `/home/box/.pi/agent/git/github.com/injaneity/zstack`. `/home/box/.pi/agent/skills/` is empty by design.

## Parity

Every host runs merged main and nothing else. Three things keep it so:

- `bin/pi-run` runs `bin/ensure-package-main` before every launch, and a bare `hosts/vm/merge_job.py` run (cron) runs it before every merge pass and restarts on the new code. It fast-forwards the package checkout to `origin/main` and never stashes, resets or forces, so a checkout it cannot move is fixed by hand.
- The `subagent` tool loads agents only from the package's `agents/`. Nothing is copied to `<pi agent dir>/agents/`, and a file left there is not read.
- cua's pre-push hook is a symlink into the package on both hosts, so the patent hold is main's too:
  `ln -sf <zstack>/hosts/vm/pre-push <root>/cua/.git/hooks/pre-push` (`<root>` is `/srv/onigiri` on the VM and `~/onigiri` on the mini). It runs `hosts/vm/patent_push.py`.

Every entry point (`bin/*`, `hosts/check-parity`, `hosts/vm/merge_job.py`, `wake.py`, the pre-push hook) prints `zstack <sha>` on stderr first, and the merge job's `last-run` carries it. `hosts/check-parity` prints it on stdout, checks all three and changes nothing but the fetched `origin/main` ref. It prints one `ok` or `FAIL` line each for the package (on `main`, clean, at `origin/main`), the hook (that symlink) and the agents dir (nothing in it that is not equal to the package's file of the same name), and exits 1 on any `FAIL`. Both host files run it at a launch, so `bin/pi-run` exits 4 and starts nothing on a host that differs. The merge job runs it on every cron run and raises an urgent `parity` wake, once an hour while it lasts. Run it by hand with `ONIGIRI_ROOT=<root> hosts/check-parity`.

## Holds file

`/srv/onigiri/hold-prs.txt`, one row per line. Only Zane edits it, except that pi may append a row relaying Zane's explicit call, with `bin/hold-row add '<row>'` on the VM (Zane, 11 Nov). The row's last column names his call and its time (`Zane 11 Nov 14:56 SGT`). The helper backs the file up to `hold-prs.txt.bak-<time>`, appends that one row, runs the merge job's `parse_holds` on the result and restores the backup if it fails. A stale row is retired the same way, never deleted: `bin/hold-row retire '<row>' '<source>'` turns it into a `# retired <source>: <row>` comment, and `bin/hold-row replace '<row>' '<new row>'` does that and puts the new row in its place, the new row's last column naming Zane's call. Any other write to the file stays blocked by rule-guard. The merge job reads three kinds: `hold | <PR> | <rules> | <note>`, `preapprove | #<PR> | <rules> | <40-char head sha> | <source>`, and `hands-off-path | <file name> | <rules> | <note>`, which holds every PR that changes a file of that name (the job waits with `who=zane`). To stop one PR, add a `hold` row. A malformed one, or a row of any other kind that names a PR number, makes the file unreadable, and then every PR counts as held. Rows about a login (`skip-author`, `review-only`) steer the hourly pickup and the merge job does not read them: `skip-author` (bots) is never picked up or reviewed, and `review-only` (teammates) gets a first review and nothing else, so a review task for one is filed, never cancelled. The mini reads a copy, `~/onigiri/sync/hold-prs.txt`, that `hosts/mini/sync-from-vm.sh` refreshes at every launch, or when run by hand after a row is added. Each run fetches into its own temp file under a lock, so launches that start together do not race and a slower fetch never replaces a newer one.

## Launching

- One launcher on both hosts: `bin/pi-run <id> <role> <brief-file>`. `~/.config/onigiri/host` holds `vm` or `mini` (`ONIGIRI_HOST` overrides it), naming `hosts/<host>/host.sh`, which sets the root and the env, so a launch from any shell (nohup, ssh, cron) loads `~/onigiri/env.sh` or `~/.profile`. It then refuses to start, before any run state or wake, when `pi --list-models` in that env lists no model of the role's provider (no credential). `bin/pi-run --help` has the run states, the exit codes and the wakes.
- The hourly pass (`skills/onigiri-mode/playbooks/hourly.md`, `bin/hourly`) runs on the mini and reaches the VM as the peer `vm=~/onigiri-vm/vm` (`ONIGIRI_PEERS` in `hosts/mini/host.sh`). Its `pickup.log`, `hourly-fingerprint.json` and `hourly-snapshot.json` are in `~/onigiri`. It collects with `bin/pi-run list exited lost`, then `bin/pi-run collect <id>` for each run it read, on each host. A lost run's collect sends its failed wake, and a collected id never starts again: a retry is a fresh id. The slot pools, `auto` and `hand`, are `[slots]` in `config/policy.toml`, counted apart across both hosts. A pool launch counts under the mini's `~/onigiri/slots.lock`, which the drain holds for its pass. The VM cannot reach the mini, so `hosts/vm/host.sh` sets `ONIGIRI_UNSEEN=mini` and a pool run started on the VM waits in its queue; `bin/hourly launch <id> vm` on the mini starts one now. An auto pause keeps new auto-pool runs off a host: a row in the mini's `~/onigiri/auto-pause`, `<host>` until the row is removed, or `<host> until <run host> <run id>` until that run is exited, lost or collected, which lifts it by itself (Zane, 12 Nov 19:01 SGT, for the VM while a bench runs there). The drain leaves that host's queued auto runs waiting, `bin/hourly launch` refuses an auto run there with a `wait` row, and the pickup launches its picks on another host. Hand and quick runs are not paused, and no running run is stopped. A row applies from the next launch decision: one written while a launch is already deciding does not recall it. `bin/hourly queue` launches both hosts' queues (queued `review/<id>/run.json` in `~/onigiri` and `/srv/onigiri`), each run on its own host, and resumes a run back from a 429 once its `resume_at` has passed. Before that it reopens, with `bin/pi-run ci`, the run that pushed each of our PRs red after the merge job's rerun: cua's pre-push hook appends `<sha> <branch>` to `review/<id>/pushed` for every push to trycua/cua from a pi run, and `ci.fix_attempts` in `config/policy.toml` caps the red heads per PR.
- The pickup pass, `bin/pickup`, runs on the mini from a launchd LaunchAgent, `com.onigiri.pickup` (`hosts/mini/install-pickup.sh on|off|status`): StartInterval `[pickup]` `interval_s` in `config/policy.toml`, no KeepAlive, no RunAtLoad. Its lock, outbox and wake reports are in `~/onigiri/pickup/` (`pickup.lock`, `state.json`, `pass-<time>.md`, `launchd.log`). It runs on the mini because the mini reaches the VM and the VM cannot reach the mini, the VM is paused between sessions, and the mini already holds the VM's ssh key, `gh` and the wake key. It reads the holds file through the VM's `bin/hourly facts`, not the synced copy. The pickup and the chat's hourly do every pickup and launch. Nothing on the VM starts pi on a schedule. To test a provider, do a real `pi -p` run, because `pi auth check --provider claude-code` reports `not_ready` even when the seat works.
- Each host keeps its own provider logins in `<agent dir>/auth.json`. Never copy one host's tokens to the other: an OpenAI refresh token is single use, so two hosts sharing one invalidate each other with `refresh_token_reused`.
- Each host also needs the packages and logins README's install section lists (pi-fff, pi-claude-code pinned, the Claude Code CLI, the ChatGPT login, `gh`). Run `bin/check-host` after setting one up, or when a launch refuses: it checks them in the launch env, makes one real call per provider, and runs `hosts/check-parity`.
- A new host also needs, before `hosts/check-parity` passes: `hosts/<name>/host.sh` and its name in `~/.config/onigiri/host`, the cua clone at `<root>/cua` with the pre-push symlink (Parity above), and on the merge host the holds file at `<root>/hold-prs.txt`.
- Wakes POST to the urgent-wake webhook with the key in `~/.config/onigiri-urgent-webhook`. Only Zane places that file, mode 0600, on each host. A host without it logs `webhook not configured`.
- `gh` runs as injaneity with `GH_CONFIG_DIR=/home/box/.config/gh HOME=/home/box`. Upstream or public posts go only through dumpling.

## Outside the package

The hourly, the launches, the merge job and collect read only these files outside zstack. Everything else they run is in `hosts/`.

- Both hosts: the credentials file (`~/onigiri/env.sh` on the mini, `~/.profile` on the VM), `~/.config/onigiri/host`, pi's `<agent dir>/auth.json`, `gh`'s login in `GH_CONFIG_DIR`, and `~/.config/onigiri-urgent-webhook`.
- The mini: the VM's ssh key `~/.ssh/onigiri_vm_ed25519` and `~/onigiri-vm/known_hosts`.
- The VM: the merge job's crontab line (in The merge job below).

Tools come from each host's install (`pi`, `gh`, `git`, `python3` 3.9 or newer, cargo's `~/.cargo/env`, the mini's micromamba bash). The mini's `/usr/bin/python3` is 3.9, which runs every script (`bin/policy` falls back to `vendor/tomli` there, and CI runs the suite under 3.9 too); its preferred `python3` is the micromamba env `py` (`micromamba create -n py -c conda-forge python=3.13` under `~/onigiri/mamba`): `hosts/mini/host.sh` puts it first on `PATH`, and `~/.local/bin/python3` links to it for shells that only load `~/onigiri/env.sh`. Data lives in `<root>`: `review/`, `pickup.log`, `events.log`, `tick/` and the cua clone. `config/state.toml` declares each state file there: its path, format, the one writer and its readers.

## Disk

`df -h /` must show well over 30G free. A run that hits ENOSPC dies mid-task. Nothing guards the disk on a schedule. The hourly routine records free space with every pickup decision. The hourly prunes finished sessions' build output and caches on either host without asking (Zane, 11 Nov). Task dirs under `/home/box/sand-data/onigiri/cua/.git/onigiri/v2/` can hold unpushed work even when their `pid` is dead, so deleting one is data deletion. List the candidates and ask Zane first.

## The merge job

`hosts/vm/merge_job.py` is the only thing that merges in `trycua/cua`. Its header has the gate, the actions and the modes (`--dry-run`, `--explain N`). Cron runs it every minute through `hosts/vm/cron-wrap.sh tick 900 2400`, which starts it once 15 minutes have passed since the last start (the VM is paused between sessions and cron skips the slots it missed), kills it after 40 minutes, and writes start and end lines to `/srv/onigiri/tick/cron.log`:

```
* * * * * HOME=/home/box GH_CONFIG_DIR=/home/box/.config/gh /home/box/.pi/agent/git/github.com/injaneity/zstack/hosts/vm/cron-wrap.sh tick 900 2400 /usr/bin/flock -n /srv/onigiri/tick/tick.lock /usr/bin/nice -n 5 /usr/bin/python3 /home/box/.pi/agent/git/github.com/injaneity/zstack/hosts/vm/merge_job.py > /dev/null 2>> /srv/onigiri/tick/tick.log
```

- trycua/cua merges through a merge queue, so `gh pr merge` can succeed before anything merged. The job logs `merge-queued cua#N` once per head, and `merged cua#N … mergedAt <time>` once GitHub says MERGED.
- Outputs: `/srv/onigiri/events.log`, and `state.json`, `last-run`, `cron.log` and `tick.log` in `/srv/onigiri/tick/`, which holds data only. There is no buffer. The five urgent kinds (`unexpected-merge`, `parity`, `holds-unreadable`, `merge-watch-overflow`, `merge-failed`) POST the webhook once per key. Every other reason is a `wait` with `who=zane`, `who=session` or none, which `--dry-run` prints and `bin/hourly` shows under needs-Zane and unstick (`ONIGIRI_MERGE_HOST`). The patent hook sends a `blocked` wake for a held push, once per branch and head. `/srv/onigiri/tick/PAUSED` stops merges and reruns.
- Don't score or flag drafts. Outside PRs go to the 3h sweep, never an urgent wake.
