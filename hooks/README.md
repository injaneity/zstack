# The rule guard

`hooks/` turns the invariants into code: a call that would break one is blocked and the reason returned, so the model sees a refusal it can act on. `guard.ts` is the Claude Code hook and `pi/rule-guard.ts` the pi extension; both call `host.ts`. The matcher is `rules.ts`, a pure module, and `tests/rule-guard.test.ts` is the list of what is and is not blocked, case by case.

## What it blocks

1. **Force-push and skipping the pre-push hook.** `git push` with a force flag or a `+refspec`, `--no-verify`, and a `core.hooksPath` override on a push. The patent hold lives in the pre-push hook, so a hook skip is a patent-hold bypass.
2. **Merging or readying in a repo the queue owns.** One merge is let through: `gh pr merge <pr> --squash --match-head-commit <head>`, with the PR's number, each option once, and nothing else but `-R <repo>` and `--delete-branch`, when `queue.py gate <pr> <head>` exits 0. That is the head the verifier passed as `auto` (or a preapproved item's), with `merge.gate_check` green, no check still running (a check run GitHub still lists as in progress but that already has a conclusion and a completion time has finished), no hold label on the PR or its issue, and not a draft. A check still running would make `gh` arm auto-merge, which could then merge a later head. Every other form is refused as before: `gh pr merge`, `gh pr ready`, and the `gh api` and GraphQL calls that do the same, in every repo the config has (`repos` in `queue.py dump`, which the extension reads once at load through `queue.py dump`; if that fails, every merge and ready is refused in every repo, since the owned repo is then unknown). CI reruns (`gh run rerun`, with or without `--failed`, and the actions rerun API calls) are not blocked: the guidance `merge-reruns` has sessions decide reruns without asking, and only real failures go to the owner. The guard can't tell a runner network failure from a failure the diff caused, so the session makes that call. Approving a fork's workflow runs (`gh api -X POST repos/<merge.repo>/actions/runs/<id>/approve`) is not blocked either: the repo guidance `merge-fork-runs` lets sessions approve outside-contributor runs there so CI runs. Review still comes before any merge, and the merge job still merges. The repo comes from `-R`, a URL, the `gh api` path, `GH_REPO`, or the `origin` remote of every directory the command might run in. A repo that can't be told is blocked, so name it with `-R` to merge elsewhere from an owned checkout.
3. **Closing an issue by hand without naming its PR.** In `merge.repo` (the config, read through the same `queue.py dump`; if that fails, every hand close is refused), `gh issue close` runs only with a `--comment` that names a PR (`#123` or a pull URL) and no `not planned` or duplicate reason, as the repo invariant `issue-close` says. The REST (`state=closed`) and GraphQL (`closeIssue`) closes carry no comment, so they are refused there, as is a REST issue update whose body comes from `--input`, which the guard can't read. The guard can't tell that the PR is ours, merged, or fixed the issue; the session checks that. The repo is told the same way as for a merge, with issue URLs too. This rule leaves PR closes alone; 4 covers them.
4. **Any push or GitHub write from a read-only item.** A review of a PR by a `people.review_only` login is claimed as read-only (`readonly` in `queue.py list`). In that item's thread, `git push` and every `gh` call that is not a plain read (`view`, `list`, `diff`, `checks`, `checkout`, a `GET` through `gh api`, and the like) is refused, so nothing is pushed to, commented on or closed. If the queue cannot be read, the thread counts as read-only. The thread puts its comments in its report (the repo invariant `teammates`).
5. **Changing a label the queue reads.** In a repo the queue owns, `gh pr create`, `gh pr edit`, `gh issue create` and `gh issue edit` are refused when a label option names `merge.hold_label`, `merge.review_label` or one of `merge.preapproved_labels`, as are `gh label delete`, `edit`, `create` and `clone` of one of them, and any `gh api` write to a labels path, which the guard cannot read. Only the owner holds, lifts a hold, forces a review or preapproves. Listing by label still runs.
6. **Moving the queue or marking a head verified from a coding thread.** In a session whose directory is a clone of a configured repo, `queue.py add` and `pass` are refused, as is `release <id>` and any command that names `queue.json` (a `write` or `edit` of that file is refused in every session), and a `gh api` write to a commit status or check run is refused. The scheduled pass runs outside any session, so the guard never sees it. `queue.py verified` is the verifier's: `queue.py` itself refuses it from the item's own thread, which it knows by the `T3CODE_THREAD_ID` the harness gives each session. So the guard refuses `queue.py verified` in a session that has no such variable, where the two can't be told apart, and refuses any command that sets or clears it.
7. **A PR title or body that breaks the repo invariant `text`.** In `merge.repo`, `gh pr create` and `gh pr edit` are refused when `--title` is not Conventional Commit syntax, or when the body (`--body`, or a `--body-file` the guard can read) has a `Co-authored-by` trailer, a "Generated with" line that links a tool, or a path under `/home/<name>/` or `/Users/<name>/`. A title or body the guard cannot read (a shell variable, stdin, `--fill`) passes: this is a lint, and the model still has the invariant. A title or body set through `gh api` is not checked.

The pre-push hook (`queue.py pre-push`) decides where a held diff is pushed, and refuses a push with a `Co-authored-by` trailer for a tool on a commit made by the pushing identity. Headers, build output and anything else the repo's own CI checks are left to that CI, which must be green before the gate opens. Model, agent and tool names in commit text are not checked, because a list of names would refuse honest commits about those tools.

Commands are split into simple commands and stripped of wrappers (`env`, `sudo`, `timeout`, `xargs`, ...) by `shell.ts`. The quoted command of `ssh`, `vm`, `bash -c`, `sh -c` and `eval` is checked too. A here-document body is data unless a shell reads it.

## Limits

It reads command text. A command built at run time (`eval "$cmd"`, a script file) is not seen, and neither is a write through Python or another interpreter. The pre-push hook and the repo's required checks stay the backstops. Children spawned by the `subagent` tool load the same package, so the guard binds them too.

The Claude Code hook also checks helpers. Claude's own Agent tool is refused for the explorer, designer and verifier, and a `delegate_task` call with the role `research`, `design` or `review` must name the model the machine file gives that role.
